# 评估：是否值得把前端迁到 Vue

> 决策时间：2026-09-09。
> 结论先行：**当前不建议整体迁 Vue**。痛点已基本收敛，迁移是拿全新回归面换已驯服的手工 DOM。此文档供日后回看。

## 背景
本项目是 Flask + vanilla JS，5 页面，无构建链，PyInstaller 打包。
近期迭代中 DOM 同步类 bug 频发（OCR 结果填卡、回填、清空、懒加载补标注等），
曾问「是否用 Vue 更好、省去 DOM 更新费心」。

## Vue 真正能解决的（响应式强项）
本质 = 「数据状态变化要同步到多个 DOM 点」的手工更新。Vue 的
`v-for` + `ref` 响应式一次消灭这类问题：
- OCR 结果填入/回填卡片输入框
- `.ocr-filled` 徽章、置信度、简繁两栏与底层数据一致
- 保存后再读回填
- 清空/懒加载补标注时的连带状态

这类 bug 约占最近问题的大头。

## Vue 解决不了的（与框架无关，必须命令式）
- canvas 画笔、切割线拖动、右键菜单定位、键盘焦点网格滚动
- adjust.js / layout.js 大量是这类交互，迁 Vue 也照写
- 4096 画布渲染、像素级操作、批处理，框架帮不上

## 成本对比
| | 现状 | 迁 Vue |
|---|---|---|
| annotate.js ~1500 行 + adjust ~1500 行 + layout 更大 | 全量重写 | 5 页组件化 |
| 无构建栈（script src + PyInstaller） | — | SFC 需上 vite 构建动打包/部署；vue.global.js 免构建但要改整套模板与事件模型 |
| 回归面 | 功能刚收敛 | 全新 DOM/事件，canvas/拖拽/菜单全要重验 |
| 工期 | — | 2–3 周级，高风险 |

## 更深的判断
最近 bug 的根本**已不是「DOM 更新烦」**，而是「谁持久化、何时读、怎么与 UI
对齐」的状态流设计。已通过以下机制收敛（对应 commit）：
- worker 每张直写 ocr_annotations.json（34918e1）
- 服务端 backfill 批量补繁体（c439688）
- 前端 done 后延迟回填 UI（4a5075a）
- 批量转换避免 N+1 并发（30be0ce）

若想进一步减少手写同步点，可做「卡片单数据源 + renderCard/patchCard 收敛函数」，
不必框架化。

## 未来真想用 Vue 的触发条件
- 新增高频交互页面（富状态 + 大量列表联动）
- 团队以框架为主，希望统一技术栈
- 愿意引入构建链、接受 PyInstaller 打包方式的调整

满足其一再评估；否则保持 vanilla + 收敛 DOM 更新的轻量手段更划算。
